# Регламент: исключение дублей уведомлений о дежурствах

Один **логический момент** (например «за 5 минут до слота 10:00» или «старт слота 10:00») не должен приводить к **двум одинаковым** исходящим сообщениям в один и тот же канал (два ЛС в Битрикс, два сообщения в общий чат и т.д.). В текущей версии backend **не ведёт** журнал «уже отправлено за (дата, слот, режим)» — за отсутствием повторов отвечает **конфигурация инициаторов** и согласованность сценариев в n8n.

См. также: [notifications-runbook.md](notifications-runbook.md), [notifications-inventory.md](notifications-inventory.md).

## 1. Термины

| Термин | Значение |
|--------|----------|
| **Инициатор dispatch** | То, что вызывает `POST …/duty-upcoming/5m`, `…/start` или общий `…/dispatch` в нужную минуту. |
| **Встроенный планировщик** | APScheduler в процессе backend (`:55` и `:00` по `TZ`), параметр `invoked_by_scheduler=True`. |
| **Внешний вызов** | OS **cron**, **n8n** (HTTP Request), ручной вызов из UI — всё с `invoked_by_scheduler=False`. |
| **Исходящие каналы одного dispatch** | JSON в **n8n** (если `N8N_DUTY_WEBHOOK_ENABLED=true` и URL задан), **Битрикс ЛС**, **Битрикс общий чат** — в зависимости от `mode` и флагов в `duty_notification_settings`. |

## 2. Матрица «кто инициирует → риск дубля»

| Инициатор A | Инициатор B (одновременно или с тем же смыслом по времени) | Риск |
|-------------|---------------------------------------------------------------|------|
| Встроенный планировщик | Внешний cron на те же `:55` / `:00` | **Высокий**: два вызова dispatch на один слот → повтор ЛС/чата/n8n. |
| Встроенный планировщик | n8n по расписанию бьёт в те же эндпоинты | **Высокий** (то же самое). |
| Два разных внешних cron (два хоста / два workflow) | | **Высокий**. |
| Один dispatch | n8n-цепочка **дополнительно** шлёт тот же текст в Битрикс параллельно backend | **Высокий** (дубль на стороне n8n + backend Bitrix). |
| Один dispatch | Только каналы backend (Bitrix ± n8n JSON) | **Низкий** (штатная модель). |

## 3. Золотое правило

**Ровно один** источник расписания для событий **`upcoming_5m`** и **`start`** по продакшену:

- либо **`scheduler_enabled=true`** и **нет** внешнего расписания на `POST …/duty-upcoming/5m` и `…/start`;
- либо **`scheduler_enabled=false`** и расписание **только** снаружи (cron или n8n), **одна** цепочка.

`TZ` внешнего cron и процесса backend должны совпадать по смыслу с [duty-time-moscow.md](duty-time-moscow.md), иначе «два разных слота» визуально превратятся в хаос даже без технического дубля.

## 4. Профили без дублей (типичный стенд)

### Профиль A — только backend

- `scheduler_enabled=true`
- Внешний cron / n8n **не** вызывают duty dispatch по расписанию.
- Битрикс: заданы `BITRIX_*`; при необходимости n8n только как **копия JSON** (`N8N_DUTY_WEBHOOK_ENABLED=true`) без второго пути в тот же чат из n8n.

### Профиль B — только внешняя автоматизация

- `scheduler_enabled=false`
- Один workflow или один crontab вызывает оба эндпоинта в `:55` и `:00` (МСК).
- Логи backend не должны содержать успешные тики встроенного планировщика для duty (его нет).

### Профиль C — n8n оркестратор, backend исполнитель

- Как профиль B; в n8n **не** дублировать отправку в Битрикс, если backend уже шлёт ЛС/чат (или наоборот: отключить Bitrix в backend и слать только из n8n — тогда согласовать шаблоны и учётные данные в n8n).

## 5. Матрица «событие → кто может слать наружу»

Один успешный **dispatch** при включённых каналах может за один раз обратиться к:

| Событие (`mode`) | n8n JSON | Битрикс ЛС | Битрикс чат |
|------------------|----------|------------|-------------|
| `upcoming_5m` | если env включён | если настроено и флаг `enabled_upcoming_5m` | нет (в текущей логике) |
| `start` | если env включён | если `enabled_start` | если `enabled_chat_on_start` |

Дубль появляется, если **два dispatch** с тем же смыслом времени оба дошли до отправки.

## 6. Чеклист проверки на стенде

- [ ] Выбран профиль A **или** B **или** C; нет двух инициаторов из §3.
- [ ] Если n8n шлёт в Битрикс отдельно от backend — в backend отключены соответствующие сценарии или в n8n отключён дубль.
- [ ] Тест: одна контрольная минута `:55` / `:00` — в ЛС и чате не более **одного** ожидаемого сообщения на событие.

## 7. Технические предохранители в коде (текущее состояние)

Идемпотентность «один слот — одна отправка» **не реализована** в БД: повторный HTTP-вызов с тем же моментом снова выполнит каналы. Регламент и мониторинг логов (`duty notify …`) — основной способ избежать дублей. Расширение продукта (ключ идемпотентности) — отдельная задача при необходимости заказчика.
