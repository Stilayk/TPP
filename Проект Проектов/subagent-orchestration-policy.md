# Политика оркестрации сабагентов (с механизмом handoff)

## 1. Цель и область применения

Политика определяет, как **координатор (менеджер)** или иной управляющий компонент распределяет задачи между агентами, управляет последовательностью их выполнения, обрабатывает промежуточные результаты и обеспечивает достижение общей цели.  
Особое внимание уделяется **handoff** — передаче результатов через структурированные файлы-отчёты, что делает процесс прозрачным, воспроизводимым и удобным для отладки.

Документ предназначен для разработчиков системы ролевых агентов и не содержит привязки к конкретному коду.

---

## 2. Основные принципы

1. **Целостность** — оркестратор гарантирует, что все необходимые шаги для достижения цели будут выполнены.
2. **Гибкость** — порядок выполнения может адаптироваться под промежуточные результаты и динамически изменяться.
3. **Прозрачность** — все решения оркестратора и действия агентов логируются. Каждый агент сохраняет свой результат в отдельный файл-отчёт, доступный для последующего анализа.
4. **Отказоустойчивость** — при сбое отдельного агента предусмотрены повторные попытки, альтернативные действия или эскалация.
5. **Минимизация вмешательства** — оркестратор не дублирует функции агентов, а лишь управляет потоком работ.

---

## 3. Типы оркестрации

### 3.1. Последовательная (Sequential)
Агенты выполняются один за другим; результат предыдущего передаётся следующему.  
**Применение:** когда задачи естественно следуют друг за другом (исследование → анализ → написание → редактирование).  
**Особенности:**  
- Оркестратор определяет порядок и дожидается завершения каждого агента.  
- Если какой-то агент не может выполнить задачу, последующие не запускаются (или запускаются с альтернативными данными).

### 3.2. Параллельная (Parallel)
Несколько агентов выполняют свои задачи одновременно, независимо друг от друга.  
**Применение:** когда нужно собрать информацию из разных источников или выполнить независимые подзадачи.  
**Особенности:**  
- Оркестратор дожидается завершения всех агентов (или заданного порога).  
- Результаты агрегируются в единую структуру.

### 3.3. Иерархическая (Hierarchical)
Оркестратор сам выступает в роли «главного агента», который разбивает задачу на подзадачи и делегирует их специализированным агентам.  
**Применение:** когда требуется сложное планирование, а агенты не взаимодействуют напрямую.  
**Особенности:**  
- Оркестратор может вызывать сам себя (рекурсивно) для вложенных подзадач.  
- Агенты не знают друг о друге, вся коммуникация идёт через оркестратора.

### 3.4. Гибридная (Hybrid / Графовая)
Комбинация последовательных и параллельных блоков, возможны условные переходы и циклы.  
**Применение:** для сложных процессов, где порядок зависит от данных (например, если результат анализа требует дополнительного исследования, запускается повторный цикл).  
**Особенности:**  
- Оркестратор использует логические условия для выбора следующего шага.  
- Возможны итерации до достижения критерия качества.

---

## 4. Выбор агента для задачи

Оркестратор принимает решение, какой агент (или группа агентов) будет выполнять задачу, на основе:

- **Роли** — определяется по описанию задачи (например, задача «собрать факты» → исследователь).
- **Навыков (умений)** — если роль не единственная, уточняется по наличию инструментов.
- **Доступности** — агент должен быть инициализирован и готов к работе.
- **Контекста** — некоторые агенты могут быть исключены из-за предыдущих результатов (например, если редактор уже правил текст, повторно вызывать его не нужно).

**Правила выбора:**
- Если для задачи подходит несколько агентов, оркестратор может:
  - выбрать одного по приоритету (заданному в конфигурации);
  - запустить всех параллельно и выбрать лучший результат (если предусмотрено сравнение);
  - использовать голосование или агрегацию.
- Если подходящего агента нет, оркестратор должен сообщить об ошибке и запросить уточнение или завершить процесс.

---

## 5. Handoff: передача результатов через единый файл истории

### 5.1. Определение и цели
**Handoff** — механизм, при котором каждый агент после выполнения своей задачи записывает результат в единый файл `HANDOFF.md`.  
`HANDOFF.md` является официальным артефактом передачи контекста между сабагентами и главным источником состояния "на каком шаге остановились".

**Цели:**
- Обеспечить прозрачность: любой участник может просмотреть промежуточные результаты.
- Облегчить отладку: при сбое видно, на каком шаге и какие данные были переданы.
- Позволить перезапуск процесса с любого этапа без повторного выполнения предыдущих агентов.
- Создать единый журнал работы агентов без необходимости перечитывать полный чат.

### 5.2. Правила хранения
- **Обязательный файл handoff**: `HANDOFF.md` в корне проекта.
- **Язык записей**: русский.
- **Порядок записей**: строго хронологический, дописывание в конец файла.
- **Изменение формата**: только оркестратор; агенты используют уже заданный шаблон.

### 5.3. Содержание записи в HANDOFF (обязательные поля)
Каждое действие сабагента фиксируется одной записью, содержащей:
- **Задача** — что именно выполнялось.
- **Время** — дата и время выполнения.
- **Кто исполнил** — агент/роль.
- **Как исполнил** — кратко: подход, инструменты, ключевые шаги.

Рекомендуемые дополнительные поля:
- **Результат** — что получено.
- **Статус**: `success` / `error` / `partial`.
- **Следующий шаг** — кто и что делает далее.

### 5.4. Использование HANDOFF последующими агентами
- Перед стартом задачи агент в первую очередь читает `HANDOFF.md`.
- Оркестратор передаёт агенту указание, с какого последнего шага продолжать работу.
- Перепроверка полного чата допускается только при явном блокере или конфликте данных.

### 5.5. Сценарии handoff
- **Последовательный**: исследователь создаёт `researcher.md`, аналитик читает этот файл и создаёт `analyst.md`, писатель читает оба и создаёт `writer.md`.
- **Параллельный**: несколько агентов создают свои отчёты независимо, затем агрегатор читает все и формирует сводный отчёт.
- **Итеративный**: редактор создаёт `editor.md` с правками, писатель в следующей итерации читает этот файл и создаёт обновлённую версию.

### 5.6. Обработка ошибок при handoff
- Если агент не может обновить `HANDOFF.md` (нет прав, конфликт записи, повреждение файла), оркестратор фиксирует блокер и приостанавливает запуск следующего шага.
- Если `HANDOFF.md` отсутствует, оркестратор обязан создать его перед продолжением работ.
- В случае частичного успеха запись всё равно обязательна, со статусом `partial` и краткой причиной.

### 5.7. Очистка и хранение
- `HANDOFF.md` хранится постоянно как журнал проекта.
- Архивация допускается только копией (например, `handoff_archive_YYYY-MM.md`) без удаления актуального `HANDOFF.md`.

### 5.8. Единый обязательный файл истории (обязательный)
Чтобы любому агенту было проще восстановить контекст "где остановились", оркестратор обязан поддерживать единый файл `HANDOFF.md`.

- **Создание на старте проекта**: если файла нет, оркестратор создаёт `HANDOFF.md` в корне проекта.
- **Обязательность обновления**: каждый агент после любых действий обязан добавить запись в `HANDOFF.md` с полями:
  - `Задача`;
  - `Время`;
  - `Кто исполнил`;
  - `Как исполнил`.
- **Конкурентная запись**: при параллельной работе оркестратор обеспечивает последовательное дописывание (очередь/блокировка), чтобы не повредить файл.
- **Безопасность**: в `HANDOFF.md` запрещено писать секреты; чувствительные данные маскируются.

## 6. Управление контекстом и передача данных (дополнение к handoff)

- Оркестратор хранит **единый контекст** выполнения (историю всех вызовов и результатов) в структурированном виде.
- При передаче данных между агентами оркестратор может:
  - передавать ссылки на файлы-отчёты (рекомендуемый способ);
  - передавать краткое извлечение из отчётов (если объём слишком велик);
  - преобразовывать формат под ожидания агента (например, из таблицы в текст).

### 6.1 Приоритет последнего handoff при старте
Чтобы агент быстрее понимал, на чём работа остановилась:
- При **каждом старте задачи** агент обязан сначала прочитать:
  - актуальный блок `Текущий статус задачи` в `HANDOFF.md`;
  - последние записи в `Лог шагов` в `HANDOFF.md`;
  - соответствующий раздел в `TASKS.md` (приоритизация и зависимости).
- Если `HANDOFF.md` и фактическое состояние расходятся, агент фиксирует это новой записью и запрашивает решение у оркестратора.
- Поясняющий текст из чата может использоваться как вспомогательная информация, но источник состояния — `HANDOFF.md`.

---

## 7. Обработка ошибок и повторные попытки

Оркестратор должен предусматривать следующие сценарии:

| Тип ошибки | Действие |
|------------|----------|
| **Агент вернул ошибку API / таймаут** | Повторить вызов до N раз (с экспоненциальной задержкой). Если не удаётся — зафиксировать сбой, перейти к резервному агенту или завершить. |
| **Агент вернул некорректный формат** | Проверить, можно ли автоматически привести к ожидаемому формату. Если нет — запросить у агента исправление (итерация). |
| **Результат агента не соответствует критериям качества** | Возможно, отправить задачу на доработку другому агенту (например, редактору) или запросить у того же агента улучшенную версию с дополнительными указаниями. |
| **Сбой оркестратора** | Должен быть механизм сохранения состояния (чекпоинты) для восстановления. |

**Политика повторных попыток:**
- Максимальное количество повторных вызовов для одного агента — 3 (настраивается).
- Если после повторных попыток агент не справляется, задача считается невыполненной.
- Оркестратор может перераспределить задачу другому агенту, если такая возможность предусмотрена.

---

## 8. Итерации и уточнения

В некоторых сценариях результат одного агента может быть отправлен на доработку другому или даже тому же агенту для улучшения.  
**Правила:**
- Итерация возможна только если это явно предусмотрено в описании процесса (например, «критик проверяет текст → писатель переписывает → критик снова проверяет»).
- Количество итераций ограничено (по умолчанию 2–3) во избежание бесконечных циклов.
- Оркестратор должен отслеживать изменения между итерациями; если улучшения нет, процесс прекращается с текущим результатом.

---

## 9. Логирование и прозрачность

Для обеспечения возможности отладки и аудита оркестратор фиксирует:

- Входную задачу и цель.
- План выполнения (какие агенты в каком порядке вызываются).
- Каждый вызов агента: время, переданные данные (ссылки на файлы-отчёты), полученный результат, статус выполнения.
- Ошибки и повторные попытки.
- Итоговый результат.

Логи должны храниться в структурированном виде (JSON, база данных) и быть доступны для анализа через интерфейс администратора. Также все файлы-отчёты сохраняются в папке `reports/` и служат долговременным хранилищем результатов.

## 10. Примеры сценариев оркестрации с handoff

### 10.1. Простой последовательный сценарий
**Цель:** Написать статью на заданную тему.  
**План:**  
1. Исследователь → сохраняет `researcher.md`.  
2. Аналитик → читает `researcher.md`, сохраняет `analyst.md`.  
3. Писатель → читает `researcher.md` и `analyst.md`, сохраняет `writer.md`.  
4. Редактор → читает `writer.md`, сохраняет `editor.md`.  
**Оркестрация:** после каждого шага оркестратор проверяет наличие файла-отчёта. При успехе передаёт следующему агенту путь к нужным файлам. При сбое любого агента процесс останавливается с сообщением об ошибке.

### 10.2. Параллельный сбор данных
**Цель:** Подготовить сводку новостей по трём разным источникам.  
**План:**  
- Запустить трёх исследователей (или одного с разными запросами) параллельно. Каждый сохраняет свой файл (`researcher_01.md`, `researcher_02.md`, `researcher_03.md`).  
- После завершения всех агент-агрегатор читает все три файла и создаёт `summary.md`.  
**Оркестрация:** оркестратор создаёт три подзадачи, ожидает их завершения, затем запускает агрегатора с указанием списка файлов.

### 10.3. Гибридный с итерацией
**Цель:** Создать маркетинговый текст, который проходит проверку на соответствие брендбуку.  
**План:**  
1. Писатель → сохраняет `writer_v1.md`.  
2. Редактор → читает `writer_v1.md`, сохраняет `editor_v1.md` с правками.  
3. **Условный переход:** если правки существенные, оркестратор передаёт `editor_v1.md` писателю для переработки. Писатель создаёт `writer_v2.md`.  
4. После максимального числа итераций (2) выдать текущий результат.  
**Оркестрация:** оркестратор управляет циклом, анализирует объём изменений (например, процент изменённого текста) и решает, продолжать итерацию или нет. Все версии сохраняются, обеспечивая полную историю.

---

## 11. Расширяемость и настройка

Политика оркестрации должна поддерживать конфигурацию без изменения кода:
- Тип оркестрации (последовательная / параллельная / иерархическая) может задаваться для каждого запроса или быть фиксированным для системы.
- Максимальное количество повторных попыток, таймауты, лимиты итераций — настраиваемые параметры.
- Возможность подключать пользовательские правила выбора агентов (например, через скрипты или конфигурационные файлы).
- Настройки handoff: формат файлов, шаблон именования, политика очистки.

---

## 12. Ограничения и допущения

- Политика предполагает, что агенты являются «честными» и возвращают результаты в оговорённых форматах.
- Не рассматриваются сценарии с динамическим появлением новых агентов во время выполнения.
- Ответственность за корректность результатов лежит на агентах; оркестратор не проверяет семантическую достоверность (но может проверять формат и наличие файлов).
- Механизм handoff предполагает, что все агенты имеют доступ к общей файловой системе (или к хранилищу отчётов).

---

Данная политика служит основой для реализации оркестратора в проекте. Механизм handoff через файлы-отчёты делает систему надёжной, удобной для отладки и позволяет легко внедрять асинхронные сценарии.
