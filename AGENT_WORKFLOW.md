# Рабочий процесс агента (репозиторий TPP)

Порядок старта, чтения контекста и критерии готовности для продолжения работы в этом репозитории. **Краткий чеклист:** `START_CHECKLIST.md`. **Политика оркестрации** — `Проект Проектов/subagent-orchestration-policy.md`. **Формат записи в лог, ACTIVE, микрошаги** — `docs/handoff-conventions.md`. **Самопроверка файлов и свежести лога:** `python scripts/check_agent_context.py` (из корня репозитория; для CI — `--strict`).

## Предстартовый обзор проекта

Перед стандартным startup-протоколом по умолчанию выполняется **обзор проекта** с фиксацией в `HANDOFF.md`.

**Полный обзор (по умолчанию):** отдельный шаг в `HANDOFF.md` — структура репозитория, ключевые модули, текущие изменения, зоны риска. После этого: `HANDOFF.md` → `TASKS.md` → `Проект Проектов/subagent-orchestration-policy.md`. Реализация до фиксации обзорного шага не начинается.

**Исключения (облегчённый старт):** без отдельного «обзорщика всего репо», если выполняется хотя бы одно из условий: пользователь явно ограничил область (конкретные файлы/директории); задача — точечная правка (один файл, очевидный объём); в `HANDOFF.md` уже есть актуальный обзор или явное продолжение с указанием путей. В облегчённом режиме в `HANDOFF.md` фиксируется кратко: какие пути затронуты и почему полный обзор пропущен.

## Проверка среды для запуска приложения

Перед **первым запуском** приложения в сессии или при шаге, где нужны сборка/тесты/dev-сервер (согласно задаче и документации проекта: `README`, `Проект Проектов/deployment_and_tz_request.md`, `docker-compose.yml`, `requirements.txt` и т.п.), исполнитель **проверяет** наличие и при необходимости работоспособность того, что требуется для этого проекта, в том числе:

- CLI и рантаймы (например Docker, Python/Node, менеджеры пакетов, команды из инструкций деплоя);
- **Плагины и расширения** среды разработки — только если без них нельзя выполнить задачу (сборка, отладка, специфичный стек);
- **Драйверы и системные зависимости** (БД на хосте, сетевые порты, при необходимости — GPU и т.д.) — если это следует из документации или шага.

**Правило отчётности:**

- Если **всё в порядке** — **не** писать в чат отдельный отчёт «проверка пройдена» и **не** добавлять в `HANDOFF.md` шаг только из-за успешной проверки.
- Если **чего-то нет**, версия не подходит, команда не в `PATH`, сервис не отвечает — **сообщить пользователю кратко** и **предложить конкретную доустановку или настройку** (что поставить, откуда, какая команда). Если из-за этого задача заблокирована — уместна **одна** запись в `HANDOFF.md` со статусом и перечнем недостающего.

## Приоритет handoff при старте

- При **каждом старте задачи** сначала прочитать:
  - строку **ACTIVE** в блоке **Якорь ACTIVE** в `HANDOFF.md` (быстрый фокус; синхронизировать с задачей при смене работы);
  - актуальный блок **Текущий статус задачи** в `HANDOFF.md`;
  - последние записи в **Лог шагов** в `HANDOFF.md`;
  - соответствующий раздел в `TASKS.md` (приоритет, зависимости).
- Если `HANDOFF.md` и фактическое состояние расходятся — новая запись в лог и запрос решения у оркестратора/пользователя.
- Текст чата — вспомогательный; источник состояния — `HANDOFF.md`.
- **Переопределение пользователем:** явная инструкция в чате (например, «сначала задача X») имеет приоритет над устаревшим **Следующий шаг** в `HANDOFF.md`; расхождение фиксируется новой записью в журнале.

## Startup-протокол нового чата (обязательно)

1. Прочитать `HANDOFF.md`: **ACTIVE**, **Текущий статус задачи**, **Следующий шаг**, последние записи **Лог шагов** (минимум 3 шага). Если файла нет — создать минимальный по `CONTINUE_PROMPT.md` / `docs/handoff-conventions.md`.
2. Прочитать `TASKS.md`: приоритет (`P1` → `P2` → `P3`), зависимости, критерий готовности целевой задачи.
3. Прочитать `Проект Проектов/subagent-orchestration-policy.md` (правила оркестрации, handoff, ретраи, логирование).
4. Синхронизировать старт: кратко зафиксировать в `HANDOFF.md`, какую задачу продолжаем и почему; при конфликте `HANDOFF.md` и `TASKS.md` источником истины считать `HANDOFF.md` и зафиксировать расхождение новой записью.

### Запрещено

- Начинать реализацию, не прочитав все три файла: `HANDOFF.md`, `TASKS.md`, `Проект Проектов/subagent-orchestration-policy.md`.
- Перескакивать на новую задачу, если в `HANDOFF.md` указан конкретный **Следующий шаг** и нет блокера (кроме явного переопределения пользователем с фиксацией в логе).
- Игнорировать критерий готовности из `TASKS.md`.
- Пропускать предстартовый обзор без оснований из раздела «Предстартовый обзор проекта» выше (полный или облегчённый с явной фиксацией в `HANDOFF.md`).
- Редактировать или перезаписывать существующие **шаги** в **Лог шагов** и блоки **Текущий статус задачи** / **Следующий шаг** без договорённости с пользователем. Разрешено: дописывать новый шаг в конец **Лог шагов**; **обновлять одну строку ACTIVE** в блоке **Якорь ACTIVE** (см. `CONTINUE_PROMPT.md`).

## Definition of Ready (старт выполнения)

- Выполнены требования раздела «Предстартовый обзор проекта»: полный обзор зафиксирован **или** облегчённый старт с явным обоснованием в `HANDOFF.md`.
- Прочитаны `HANDOFF.md`, `TASKS.md`, `Проект Проектов/subagent-orchestration-policy.md`.
- Выбрана одна текущая задача с понятным критерием готовности из `TASKS.md` (или явно заданным пользователем).
- В `HANDOFF.md` добавлена запись о старте работ (задача, время, кто, как).

## Definition of Done (завершение шага или задачи)

- Выполнен критерий готовности по `TASKS.md` (или согласованный с пользователем эквивалент).
- В `HANDOFF.md` есть запись о результате (статус `success` / `error` / `partial`, при необходимости — пути к новым артефактам; см. `docs/handoff-conventions.md`).
- В журнал не попали секреты; при ошибке указан блокер или следующий шаг.
